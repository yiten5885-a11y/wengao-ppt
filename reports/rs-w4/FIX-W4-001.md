- **日期**：2026-10-24
- **归属**：W4（工作台与集成）
- **优先级**：P0（阻断所有材料导入、PPT 上传与开始制作）
- **状态**：已修复、全量回归通过、现场双界面走查验收通过

## 一、问题背景与根因定位

### 1. 现象
- 在 8823 本地工作台首页 `/` 与新界面 `/ui`，材料导入（.md / .docx）、演示工作室上传 PPTX、点击"开始制作"均无响应，直到客户端超时报错。
- 所有 GET 接口正常，空请求体的 POST（如探测请求）立即返回 400，但只要带请求体即阻塞挂死。

### 2. 根因
1. **前置入口无条件读空请求体**：
   `workbench/server.py` 的 `do_POST` 第一步调用 RS-9 新界面分发器 `ui_api.dispatch_post(self, path)`。在旧代码中，`workbench/ui_api.py` 的 `dispatch_post` 函数第一行无条件调用 `handler._body_json()`，不论路径是否属于新界面，均按 `Content-Length` 将底层 socket 数据读光。当请求不属于新界面路由时返回 `False`，随后的旧路由处理函数（如 `_upload_bytes`、`_make_start` 等）再次尝试从 `self.rfile` 读取时，套接字已无数据，线程永久阻塞在 `sock_recv_into` 直至客户端超时断开。
2. **新旧路由抢占**：
   新界面的 `dispatch_post` 挂载了 `/api/jobs/<id>/export` 与 `/api/jobs/<id>/cancel`，直接截断了排在后面的 `server.py` 原生 CLI 调度路由 `/api/jobs/([A-Za-z0-9-]+)/(run|validate|cancel|export)`，破坏了旧工作台首页 `/` 的导出与取消流程。
3. **缺乏防二次消费保护机制**：
   Handler 层面没有针对请求体流式消费的状态标记，发生误读时只能隐蔽挂起，无法快速失败。

## 二、改动内容与实现方案

### 1. 必做项 A：新入口仅命中自有路由才读取请求体（按路由先判后读）
- **文件**：[workbench/ui_api.py](file:///Users/huangyingteng/WorkBuddy/2026-10-12-00-54-41/wengao-ppt/build/wengao-visual-v13-material-fix/workbench/ui_api.py)
- **改动**：
  - 显式声明新界面认领的 POST 正则路由表 `_POST_PATTERNS`：
    - `r"^/api/ui/jobs/([A-Za-z0-9-]+)/(decisions|page-ops|export|cancel|retry)$"`
    - `r"^/api/jobs/([A-Za-z0-9-]+)/(decisions|page-ops|retry)$"`
  - 提供 `_owns_post(path: str) -> bool` 预检函数。
  - 在 `dispatch_post` 最开头执行 `if not _owns_post(path): return False`，在触碰 `_root_of(handler)` 与 `_body_json()` 之前彻底放行所有非自有路由。`handler.rfile` 游标完全保持为 0。

### 2. 建议项 B：请求体只读一次保护机制（快速失败与缓存）
- **文件**：[workbench/server.py](file:///Users/huangyingteng/WorkBuddy/2026-10-12-00-54-41/wengao-ppt/build/wengao-visual-v13-material-fix/workbench/server.py)
- **改动**：
  - 新增自定义异常 `BodyAlreadyConsumedError`。
  - 在 `do_POST` 与 `do_GET` 每次请求入口重置 `self._body_consumed = False` 与 `self._body_cached_json = None`（解决 HTTP/1.1 Keep-Alive 跨请求连接复用状态继承问题）。
  - `_body_json(self)`：
    - 首次读取后缓存解析结果至 `self._body_cached_json`，后续多次读取直接返回缓存，不重复移动底层 `rfile`。
    - 若已被流式上传标记 `self._body_consumed = True`，抛出 `BodyAlreadyConsumedError`。
  - 流式读取方法（`_upload_bytes`、`_asset_upload`、`_native_playback_upload`）：
    - 读取前检查 `if getattr(self, "_body_consumed", False)`；若已被前置逻辑读取，立即返回 HTTP 500（`WB.BODY_ALREADY_CONSUMED`），不再陷入 `sock_recv_into` 挂起。
    - 首次读取时设置 `self._body_consumed = True`。
  - `do_POST` 捕获 `BodyAlreadyConsumedError`，统一返回 HTTP 500 `WB.BODY_ALREADY_CONSUMED`。

### 3. 必做项 C：路由抢占解决方案（选择与理由）
- **文件**：
  - [workbench/ui_api.py](file:///Users/huangyingteng/WorkBuddy/2026-10-12-00-54-41/wengao-ppt/build/wengao-visual-v13-material-fix/workbench/ui_api.py)
  - [workbench/ui/actions.js](file:///Users/huangyingteng/WorkBuddy/2026-10-12-00-54-41/wengao-ppt/build/wengao-visual-v13-material-fix/workbench/ui/actions.js)
- **选择方案**：**推荐方案 —— 新界面 POST 路由统一归入 `/api/ui/...` 独立命名空间，旧路由完整保留**。
- **选择理由**：
  1. **职责与契约清晰**：新界面 `/ui` 的导出与取消包含 RS-9 的特有逻辑（如包含来源与署名清单 `attribution`、SSE 状态流取消请求标记），而旧路由 `/api/jobs/<id>/(cancel|export)` 严格执行原生 CLI runner（`cli(ROOT, "export", ...)`）。二者返回数据结构和门禁契约不同，统一使用 `/api/ui/...` 前缀实现完全解耦。
  2. **零歧义、零启发式猜测**：备选方案需要在同一个 URL 路径下猜测调用方身份（例如检查前端传参、特定 Header 或数据库记录类型），极易在边缘场景产生漏判。独立前缀在路由层实现静态确定性分流。
  3. **无缝双向兼容**：
     - 旧工作台 `/` 及所有旧自动化脚本调用 `/api/jobs/<id>/export` 和 `/api/jobs/<id>/cancel` 毫无影响，按旧 runner 原生契约工作。
     - 新工作台 `/ui` 前端（`actions.js`）调用 `/api/ui/jobs/<id>/export` 与 `/api/ui/jobs/<id>/cancel`，完整享有 RS-9 署名清单与取消状态流联动。
     - 针对无冲突的新特性端点（`decisions`、`page-ops`、`retry`），同时兼容 `/api/ui/jobs/...` 与 `/api/jobs/...`。
